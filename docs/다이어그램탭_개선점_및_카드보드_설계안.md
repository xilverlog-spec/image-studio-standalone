## 2부. 카드 보드 설계안

### 2-1. 참고 보드에서 뽑은 문법 (8개 부품)
| 부품 | 모양 | 예 |
|---|---|---|
| 머리 | 구분 라벨 + 큰 제목(일부 강조) | 전 쪽 → 1부 #1 (페이지 모드 제목 슬롯 사용) |
| 핵심 가치 띠 | 3~6개 박스: 번호/키워드 + 아이콘 + 1~2줄 | B23·B25 "설계주안점" 괄호 박스, A25 01~03, C20 인증 5칸 |
| 히어로 | 큰 이미지(아이소·단면·입면) + 번호 마커 + 좌우 리더선 라벨 | B23, C20, B25 |
| 아이콘 목록 | 번호 박스 + 아이콘 + 제목 + 한 줄 | C20 좌측 10개, B25 48개 |
| 카드 격자 | 3~6열. 카드 = 헤더(아이콘+제목) + 소도식 칸 1~3 + 불릿 1~2줄 | B23·B25·B26·A25·C20 |
| 3열 가치 카드 | 열 머리(작은 문구+큰 키워드) + 큰 그림 + [소도식·제목·설명]×3 | D17·E17·F18 |
| 정보 표 | 라벨–값 2열 | A25·B23 우측 |
| 프로세스 띠 | 화살표 라벨 띠 | E12, C20 분류 칩 |

공통 스타일: A3 가로, 카드 헤더는 회색 띠 또는 분류색 띠, 번호 마커 사각/원, 불릿 `·`, 강조색 주황·파랑·초록, 흰 바탕.

### 2-2. 앱 안의 위치
- 새 종류 `cards`("기술·상품 카드 보드")를 `spec.js`에 등록해 **기존 종류와 같은 흐름**을 탄다: 설명 입력 → AI가 구조(JSON)만 작성 → `normalize` → 프로그램이 SVG를 그림 → 글자는 항상 프로그램 글자(깨지지 않음) → 글자 수정 폼 + 구조형 편집기로 계속 편집.
- 페이지 모드에서는 **칸 하나를 채우는 본문**이다. 제목은 페이지 머리를 쓰므로 `spec.title`은 비운다(기존 종류와 같은 규칙). 칸의 가로세로 비율에 맞춰 열 수를 자동으로 정한다(기존 `bestCols`와 같은 방식).
- 글자 크기 위계 판정(`judgeTextPt`)은 그대로 적용된다.

### 2-3. 스펙(JSON) 초안
```
{ type: 'cards', accent: '#F28C28',
  bands: [                                   // 위에서 아래로 쌓는 띠, 최대 4개
    { kind: 'keypoints', style: 'bracket|tabs|kpi', items: [{ no, title, text, icon }] },   // 최대 6
    { kind: 'hero', callouts: [{ no, side: 'left|right', title, text }], side: 'table|legend|none',
      legend: [{ no, icon, title, text }], table: [[라벨, 값]...] },                         // 그림은 사용자 이미지
    { kind: 'cards', tone: 'gray|pink|green|blue', label, cards: [
        { title, icon, sub, slots: [{ kind: 'icon|image|empty', icon, caption }], bullets: [..] } ] },  // 카드 최대 12
    { kind: 'columns3', cols: [{ lead, key, image, rows: [{ title, text, slot }] }] },
    { kind: 'process', steps: [{ label, text }] } ] }
```
한도(normalize가 자름): 띠 4 · 카드 12 · 불릿 2줄(줄당 40자) · 키포인트 6 · 아이콘은 라이브러리 목록 안에서만.

### 2-4. 시작 틀(프리셋) 5종 = 제한의 구현 수단
| 틀 | 구성 | 참고 쪽 |
|---|---|---|
| P1 계획 요약형(구조·토목) | keypoints(5) + hero(콜아웃, 표) + cards(6) | B23, A25 |
| P2 친환경·에너지형 | keypoints(인증 5) + hero(번호 마커)+legend(10) + process + cards(4) | C20, B26 |
| P3 설비·시스템형 | keypoints(6) + hero(단면 + 아이콘 목록) + cards(2행×6) | B25 |
| P4 분야별 계획형 | hero(단면) + 분류 칩 + cards(3, 표 포함) | C19 |
| P5 3열 가치형 | columns3(차별성·분양성·경제성) | D17, E17, F18 |

사용자는 틀을 고르고 내용을 쓰면 AI가 채운다. 틀 밖의 구성은 만들지 않는다.

### 2-5. 소도식 칸 정책 (가장 어려운 부분)
참고의 소도식은 대부분 그림·사진이라 앱이 자동으로 그리지 못한다. 그래서:
1. 기본은 **아이콘 타일**(자동, 항상 깨끗)
2. 사용자 이미지로 **교체**(끌어놓기·붙여넣기, 기존 "내 이미지 넣기"·자르기·바꾸기 재사용)
3. 후속: 같은 앱의 다른 종류(배치 개념도·매스·조닝) 결과를 소형으로 넣기
4. 빈 점선 칸 — 저장 시 숨김/표시 선택

히어로 그림은 앱이 만들지 않는다(사용자 이미지). 도면 위 표시로 만든 결과를 넣을 수 있다.

### 2-6. AI 단계
- 입력은 사용자가 쓴 설명 **텍스트만** 보낸다(이미지 전송 없음). 현재 다른 종류가 쓰는 호출 경로를 그대로 쓴다.
- AI는 구조(제목·불릿·아이콘 이름·강조어)만 정하고, 글자 줄바꿈·배치·그리기는 프로그램이 한다.

### 2-7. 단계와 완료 기준
| 단계 | 내용 | 완료 기준 |
|---|---|---|
| M1 | 렌더 코어 `cardboard.js`: normalize + 5개 부품 + 글자 줄바꿈 + 아이콘 40개 + 예시 5개 | 회귀 시험(NaN·넘침·긴 글자·빈 입력) 통과, 예시 5개가 틀대로 나옴 |
| M2 | 앱 연결: 종류 등록·AI 프롬프트·선택 화면·글자 폼·카드 추가/삭제·페이지 모드 열 수 | 설명만 넣어 5개 틀이 만들어지고 편집·저장됨 |
| M3 | 이미지 슬롯·히어로: 이미지 넣기, 번호 마커+리더선 드래그 | 사용자 이미지로 교체·저장 |
| M4 | 검증: 참고 카드 보드 14쪽을 같은 내용으로 재현해 비교 | 육안 비교 + 편집성 점검 |

## 3부. 인터뷰 결정 기록

| 회차 | 질문 | 결정 |
|---|---|---|
| 1 | 먼저 할 묶음 | **보드 틀**(1부 A: #1~#4)을 1순위로 |
| 1 | 개요표 | **간단한 표 요소를 추가**(라벨–값 2열. 계산·병합셀·간트는 제외) → 1부 #8 지원으로 확정 |
| 1 | 소도식 칸 기본값 | **아이콘 타일**(이미지를 넣으면 교체) |
| 1 | 아이콘 | **오픈소스 세트 일부 포함**(MIT/ISC, 건축 관련 약 80개). 포함 전 라이선스 확인 |
| 2 | 페이지 머리·꼬리 요소 | **구분 라벨 + 제목 강조**, **꼬리말(프로젝트명 + 쪽번호)**. (오른쪽 위 도면 라벨·방위표·스케일바는 이번 범위에서 제외 — 후속) |
| 2 | 칸 라벨 모양 | **선 사이 라벨(A6형)**: 가로선 사이 "STEP 01. GROUND" + 굵은 한 줄 제목 + 작은 설명 2줄 |
| 2 | 기본 글꼴 | **Pretendard** (앱에 이미 있음. 저장한 SVG는 Pretendard가 설치된 PC에서 열어야 그대로 보임) |
| 2 | 배치 프리셋 추가 | **큰 칸 + 아래 띠 4칸**(3·5칸도 같은 틀에서 선택), **왼쪽 세로 4칸 + 오른쪽 큰 칸**. (위 4열+와이드, 3열×3단 격자는 후속) |
| 3 | 칸 라벨 번호·접두어 | **자동 채움 + 직접 수정**: 칸 순서대로 01, 02… 자동, 접두어(STEP / ISSUE / 배치전략 / 없음) 선택, 글자는 클릭해서 바로 고침 |
| 3 | 제목 강조 | **{중괄호} 표기 + 주황색 굵게**(색은 설정에서 변경) |
| 3 | 바탕 정책 | **페이지 모드에서는 자동 투명**(보드의 흰 종이 위에 그림만). 단독 저장은 예전처럼 크림색 |
| 3 | 쪽번호 | **직접 숫자 입력**(설정 칸, 두 자리 `02`. 비우면 프로젝트명만) |
| 4 | 번호 마커 모양 | **검은 원(흰 숫자) 기본 + 색 사각 선택**(색은 속성에서) |
| 4 | 번호 규칙 | **자동 증가 + 지우면 뒤 번호를 다시 맞춤**, 번호는 직접 고칠 수도 있음 |
| 4 | 리더선 라벨 | **굵은 제목 + 설명 1~2줄 + 직선 + 끝점**(선은 직선/꺾은선 선택) |
| 4 | 복수 선택 회전 | **선택 묶음의 가운데를 중심으로 함께** 회전(구조형). 손스케치는 한 개씩 |
| 4-2 | 개요표 위치 | **둘 다**: 편집기 요소(그림 안) + 페이지 칸 종류(표 전용 칸) |
| 4-2 | 개요표 열 수 | **2~4열 지정**(열 너비는 글자 길이에 맞춰 자동) |
| 4-2 | 개요표 스타일 | **둘 다 선택 가능**: 회색 라벨 열+가는 선(B23형) / 제목 색 띠+줄무늬(면적표형) |
| 4-2 | 개요표 편집 | **속성 패널 행 목록 + 그림에서 셀 더블클릭 + 엑셀·한글 표 복사해 붙여넣기** |
| 4-2 | (메모) 개요표 단계 | 작업이 커져 **v1 = 편집기 요소(2~4열, 두 스타일, 행 목록+더블클릭)**, **v2 = 붙여넣기 변환 + 페이지 칸 종류**로 나눠 진행. 병합 셀·계산은 여전히 제외 |
| 5 | 카드 보드 v1 시작 틀 | **계획 요약형 + 설비·시스템형**(P1+P3: 핵심 가치 띠 + 히어로 + 카드). 3열 가치형(P5)·친환경형(P2)·분야별형(P4)은 v2 이후 |
| 5 | 입력 방식 | **AI 초안 + 폼으로 수정**(설명 텍스트만 전송, 글자 수정 폼·그림 위 더블클릭으로 고침) |

### 7-9. 참고사례가 결과물 품질로 이어지게: 도면 위 표시(동선·구역) 측정과 개선 (2026-10-26)
사용자 지적: "참고사례 폴더를 읽음으로써 결과물의 퀄리티가 좋아져야 한다." 7-8 까지의 반영은 **그림이 그려지는 모양**(선·표·색)이 대부분이었고, 소재 이미지에서 무엇을 뽑아 어떻게 구성하느냐(삽도의 22% 1위인 동선·구역 표시도)는 측정하지 않았다. 그래서 **같은 입력·같은 시드로 전/후를 실제 AI 로 돌려 비교**하는 방식으로 바꿨다.
- **시험 입력(사용자 지정)**: 사내 계획도면 PDF 의 2쪽 배치도(1/1,000)·4쪽 지상1층 평면도(1/500). 사내 자료라 **이미지·프로젝트명은 저장소에 두지 않았다**(작업 폴더 밖). 두 쪽은 이 앱의 도면 위 표시 흐름대로 무료 Gemini 에 전송됐다. 요청문은 두 가지: 배치도 "차량 진출입·보행자 동선 구분, 주출입구→사무동·연구동 주 동선 강조", 평면도 "연구·실험 공간 기능별 구역 + 주출입구→이음마당→각 실 주 동선".
- **전(이전 방식) 결과의 문제 6가지**: ① 구역 색이 방 벽에 안 맞고 흐리게 번짐 ② 방과 색의 대응 오류(지시 '노랑'인 방이 파랑, '보라'인 방이 노랑…) — 범례는 완성 그림을 다시 보고 고쳐서 뜻이 섞임 ③ 주 동선 화살촉이 건물 반대쪽을 가리키고 순환선엔 화살촉 없음 ④ 화살표가 기존 글자('주출입구')를 가림 ⑤ 화살표가 손으로 그린 듯 울퉁불퉁하고 도면 길을 따르지 않음 ⑥ **원본 훼손**: 회색 도로 (184,184,184)→(147,146,146), 화소의 16~18%가 크게 변함(곱하기 판이 Qwen 결과에서 오기 때문).
- **원인**: 구역 칠을 이미지 편집 모델(Qwen)에게 맡긴 것. 사내 문법(7-6)이 "단색 구획 + 범례"인데 반투명 안개 칠이 나왔고, 방-색 대응은 모델이 임의로 틀렸다.
- **개선 A(구현·배포)**: AI 는 '무엇을'만 정하고 칠은 코드가 한다. 새 모듈 `backend/services/diagram_zone.py` — Gemini 가 구역별 방 이름·방 이름 상자(`label_box_2d`)·방 전체 범위(`room_box_2d`, 0~1000)를 주면 ① 상자를 벽선에 붙이고(가까운 곳 ±4.5%는 옅은 회색 벽선까지, 못 찾으면 ±1.55% 안의 뚜렷한 선 가운데 가장 가까운 것) ② 상자 안에서 방 이름과 이어진 칸을 구멍(가구선·글자) 메워 단색(사내 옅은 면 평균에 맞춘 6색)으로 칠한 '곱하기 판'을 만들어 Qwen 의 채움 판 대신 쓴다. 칸이 상자의 15% 미만이면 상자 전체. 칠은 상자 밖으로 못 나가므로 문·개구부로 새도 갇힌다. 구역만 요청하면 **Qwen 을 아예 부르지 않는다(30초~1분)**, 동선이 있으면 Qwen 은 화살표만 그린다. 구역 범례는 코드가 만들어 범례 확인(Gemini 두 번째 호출)이 필요 없다. 구역을 요청하지 않은 동선 표시(배치도)도 곱하기 판을 1.0 으로 둬 **원본 색이 바뀌지 않는다**(회색 도로 184→184, 크게 변한 화소 16.3%→0.6%).
- **측정(평면도, Gemini 상자에 일부러 오차를 줌)**: 칠한 칸의 겹침률(기준=오차 없음) ±25px 에서 0.84 → 0.97(벽 판정 120→170, 허용 거리 14→28px, 가장 가까운 뚜렷한 선, 칸 폴백 기준 60%→15%). 구역만 3회 실제 실행 23·51·30초, 방 12개 모두 방 이름과 일치하는 색.
- **한계**: 구역 묶음은 Gemini 판단이라 실행마다 다름. 벽이 없는 열린 공간·L자 방·흐린 벽은 범위가 넓게 잡힐 수 있음. 동선 화살표는 여전히 Qwen(방향·경로 오류·글자 가림). "일부 영역 다시 그리기"는 아직 예전 Qwen 방식. 시험 입력이 2쪽이라 일반화 정도는 더 시험해야 함.
- **다음(B, 미구현)**: 동선 경로도 코드가 찾는다 — Gemini 가 출발·경유·도착을 방 이름으로 주면 코드가 복도·도로를 따라 길을 찾고 사내 문법(굵기 1.5~3pt, 점선 35%, 화살촉, 흰 테두리)으로 벡터 화살표를 그린다. 방향 오류·글자 가림·울퉁불퉁함이 해결될 것으로 예상(미측정).
